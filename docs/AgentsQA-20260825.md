核心结论：

- 本机 MX350 仅 2 GiB 显存，配合 15 GiB 内存和约 58 GiB剩余磁盘，不支持论文级训练或完整 RPDiff 评测。宿主 NVIDIA 驱动正常。
- 未安装不可用的完整 CUDA 环境；保留了 Git 忽略的 `.venv` CPU 审计环境，约 2.1 GiB。
- 官方克隆已完成，HEAD 与本仓库中的官方祖先均为 `c4a2f79`。官方发布确实缺少 TAX-DPD 核心 wrapper、正式评测配置、预训练权重和完整仿真链。
- 当前本地 `tax3d_v2.py` 是重建实现。其 GMM→局部坐标链未接通，fixed 模型忽略 `noisy_goal`，TAX3Dv2 评测绕过 GMM，并依赖真值进行 WTA 选择。
- 当前 28.6% 使用 Hard-Multi 数据，而论文 95% 是 Multi-MedRack；数据、划分与仿真协议不一致，二者不能直接视为同任务复现差距。
- 当前普通 SVD 不等价于论文的 RANSAC-SVD；此外 `T_err` 实际只是质心位移范数，并非完整 SE(3) 平移误差。

验证已通过：

- CPU PyTorch 前向/反向
- Hydra 显式配置组合
- MuJoCo、PyBullet DIRECT 单步
- `tests/simple_test.py`：`1 passed`
- `pip check`：无已安装依赖冲突
- 关键 Python 文件语法与文档格式检查

未安装 PyTorch3D、PyG/R-PAD、Open3D 等大型依赖，因此 `.venv` 明确不是完整复现环境。Git 状态仅新增上述文档，没有改动任何既有 tracked file。

> 初步结论已经很清楚：刚体任务属于“高但可工程化”的迁移，可变形 DEDO 则接近重建一套新 benchmark。尤其当前环境固定的是 MuJoCo 2.3.7，而较现代的原生 `flex/flexcomp` 可变形机制从 MuJoCo 3.0 才加入；若迁 DEDO，连依赖基线都要先升级。

</details>

结论：RPDiff 刚体任务可以迁移，属于“高但可工程化”；DEDO 可变形任务则是“很高复杂度，接近重新实现环境”。迁移后的结果应视为新的 MuJoCo benchmark，不能直接与论文的 PyBullet 成功率比较。

### 复杂度判断

| 目标                                                         | 复杂度                    | 核心原因                                                                   |
| ------------------------------------------------------------ | ------------------------- | -------------------------------------------------------------------------- |
| 在 MuJoCo 中加载 RPDiff 资产、重置位姿、执行一次预测 `SE(3)` | 中                        | 几何和 TAX-DPD 输出可复用，主要是 MJCF、坐标和相机适配                     |
| 完整迁移 RPDiff controller、接触重试和 success predicate     | 中高到高                  | 窄间隙碰撞、力阈值、摩擦、相机分割和终态判据均需重写、校准                 |
| 让 MuJoCo RPDiff 与论文 PyBullet 数值等价                    | 很高，无法天然保证        | 换求解器后，卡住、滑动、插入和释放稳定性的边界都会改变                     |
| 仅在 MuJoCo 中加载 DEDO 布料并读取顶点                       | 中，前提是升级 MuJoCo 3.x | OBJ 几何可复用，但当前仓库固定的 2.3.7 缕缺现代 Flex                       |
| 完整迁移 DEDO HangProcCloth、DP3、抓取和判分                 | 很高                      | 布料材料、动态顶点锚定、拓扑编号、自碰撞、机器人控制和策略分布全部耦合     |
| 在 MuJoCo 2.3.7 上保持 DEDO 行为                             | 极高，不推荐              | 只能用旧 `composite cloth/grid` 近似，不能视为 Bullet soft body 的等价实现 |

### 两种引擎的设计哲学

| 维度         | PyBullet / Bullet                                                      | MuJoCo                                                                          |
| ------------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 核心定位     | 通用、实时、覆盖面广的物理引擎；游戏、机器人、刚体和软体都能快速组合   | 面向机器人动力学、控制、估计和优化的高效多体系统                                |
| 建模方式     | “可变世界”：运行时加载/删除物体、修改动力学、创建约束、直接重置姿态    | “编译模型”：MJCF/URDF 先编译为固定结构的 `mjModel`，状态放在 `mjData`           |
| API 风格     | 命令式：`loadURDF`、`loadSoftBody`、body ID、`stepSimulation`          | 模型式：joint、actuator、equality、sensor 先声明，再 `mj_step`                  |
| 接触求解     | 常用 sequential impulse、PGS/LCP 风格迭代约束；ERP、CFM、margin 等调参 | 软约束与优化式统一求解；常用 Newton，也支持 CG/PGS，以 `solref/solimp` 控制接触 |
| 可变形体     | `loadSoftBody`、动态顶点 anchor 等接口直接，适合快速搭建               | MuJoCo 3.x 才加入原生 `flex/flexcomp`；更模型化，但不是 Bullet API 的直接替代   |
| 运行时改拓扑 | 很自然                                                                 | 通常需要修改 MJCF/MjSpec 并重新编译                                             |
| 优势倾向     | 快速构造复杂、动态、异质场景                                           | 规范化机器人模型、高效控制、动力学分析                                          |
| 常见误解     | 灵活不等于物理参数容易复现                                             | MuJoCo 也不等于自动“更真实”；精度仍取决于模型和参数                             |

一句话概括：

> PyBullet 把仿真看成一个可以不断发命令修改的世界；MuJoCo 更像一个预先编译好的动力学系统。

### RPDiff：为什么相对可迁移

有利的一面是，TAX-DPD 网络、点云输入和最终预测的 `SE(3)` 都与物理引擎基本解耦。按照公开 RPDiff 机制，评测执行主要使用 floating gripper/直接物体控制，而不是完整机械臂规划，因此不一定需要先迁移 Franka IK 和真实抓取链。

主要工作在以下部分：

1. 碰撞几何

   MuJoCo 普通 mesh 碰撞主要使用凸包。若把 rack、杯把、书架或柜体作为单个非凸 mesh 导入，孔洞和开口可能直接被凸包封住。需要：
   - 用 box、cylinder 等 primitive 重建；
   - 或进行凸分解，组合多个 geom；
   - 必要时评估 MuJoCo 3.x 的 SDF 等方案。

   对挂杯、插书和入柜这类窄间隙任务，这是最大风险。

2. Controller 和接触重试

   RPDiff 公开 controller 包含 pre-placement、直线推进、接触停止、回退、横向/旋转扰动和多次重试。Bullet contact force 阈值不能直接照搬到 MuJoCo，需要重新标定 `solref/solimp`、摩擦、时间步和停止阈值。

3. 动态约束和碰撞过滤

   Bullet 的 fixed constraint、运行时 collision filter，要改成 MuJoCo 的 slide joint/mocap body、可开关 equality，以及 `contype/conaffinity` 等机制。

4. 相机和点云

   两个引擎的相机轴、深度缓冲转换、segmentation ID 和 quaternion 顺序不同。需要对 RGB、depth、instance mask、反投影点云做逐项回归。

5. Success predicate

   `touching_surf`、upright、collision-free、释放后稳定等判据必须移植，并在 oracle goal 上先验证，不能只看最终渲染图是否相似。

此外，当前仓库没有论文使用的精确 RPDiff mesh、split 和 controller 配置。因此现在只能实现“相似的 MuJoCo RPDiff”，还不能认证为原任务的后端迁移。

### DEDO：为什么近似重新实现

DEDO 对 PyBullet soft-body contract 绑定得非常深：

- [`init_utils.py`](./third_party/dedo/dedo/utils/init_utils.py:78) 用 `loadSoftBody` 配置 mass-spring、弯曲、阻尼、摩擦和自碰撞；
- [`tax3d_proccloth_robot_env.py`](./third_party/dedo/dedo/envs/tax3d_proccloth_robot_env.py:115) 把指定 cloth vertex 动态连接到机器人 link；
- [`tax3d_env.py`](./third_party/dedo/dedo/envs/tax3d_env.py:503) 每一步直接读取保持拓扑编号的完整 mesh，作为 DP3 observation；
- [`tax3d_proccloth_env.py`](./third_party/dedo/dedo/envs/tax3d_proccloth_env.py:373) 又用真实 loop vertex IDs 做终态判分。

而当前环境固定 [`mujoco==2.3.7`](./pixi.toml:83)。MuJoCo 的原生 `flex/flexcomp` 是 3.0 才引入的，因此合理路线是单独建立 MuJoCo 3.x 环境，而不是强行在 2.3.7 上模拟。

即使升级后，仍需解决：

- Bullet stiffness 与 MuJoCo stretch/bend elasticity、thickness、contact 参数没有一一映射；
- cloth OBJ 顶点不能被重排，否则 anchor 和 loop 标签全部失效；
- `createSoftBodyAnchor/removeConstraint` 要改成可启停的 flex node/equality；
- 程序化生成不同拓扑时，MuJoCo 通常需要重新生成并编译模型；
- MuJoCo 相机分割和 rigid anchor PCD 要重写；
- DP3 原策略面对新的布料动力学会产生 distribution shift，通常需要重新生成示范并训练。

所以 DEDO 的“资产能加载”相对容易，“任务和策略行为等价”很难。

### 建议路线

如果目标是复现论文数字，继续使用 PyBullet。

如果目标是建设未来的 MuJoCo 平台，建议：

1. 先迁 RPDiff EasyRack，使用 oracle goal 验证碰撞和判据；
2. 再把同一批缓存的 TAX-DPD `SE(3)` 同时送入两个引擎，区分模型误差和物理差异；
3. 将 MuJoCo 结果单列为新 backend；
4. DEDO 单独升级到 MuJoCo 3.x，先做固定单块 HangProcCloth、虚拟 anchor、无机器人版本；
5. 依次验证顶点映射、自由垂落、拉伸/弯曲、anchor attach/release、自碰撞和 success predicate，最后才接 DP3。

仓库现有的资产与迁移边界汇总可参见[技术审计 §3.8–3.10](./docs/TECHNICAL_ARCHITECTURE_AND_REPRODUCTION_AUDIT_2026-08-14.md:1018)。
